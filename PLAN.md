# Lora Face Select Lite — план окремого проєкту

## 1. Рішення

Окремий CPU-first застосунок для вибору фотографій однієї людини для Face LoRA на слабкому ноутбуці створити реально.

Основна заміна:

- InsightFace `buffalo_l` -> OpenCV YuNet + SFace;
- ONNX Runtime як окрема залежність не потрібен: моделі запускаються через OpenCV DNN;
- аналіз виконується на зменшеній копії зображення, а у результат копіюється оригінал;
- інша логіка відбору відтворюється незалежно, без імпорту коду з поточного застосунку.

Перш ніж вважати заміну успішною, її треба перевірити на реальних фото користувача. Найбільша невизначеність — точність розпізнавання людини на профільних, темних, розмитих і частково закритих обличчях, а не можливість запуску на CPU.

## 2. Ціль і межі MVP

MVP повинен:

1. Приймати папку з кандидатами, 1–5 референсів, кількість фото та output-папку.
2. Знаходити всі обличчя через YuNet.
3. Вирівнювати кожне обличчя за 5 landmark-точками та отримувати SFace embedding.
4. Вибирати обличчя, найбільш схоже на усереднений reference embedding.
5. Відсіювати неправильну людину, фото без облич, надто малі обличчя та непридатні кадри.
6. Окремо складати фото з кількома обличчями для ручного перегляду.
7. Оцінювати різкість, експозицію, роздільність обличчя, запас навколо обличчя і масштаб кадру.
8. Виявляти майже однакові фото через perceptual hash.
9. Набирати різноманітний набір за масштабом, ракурсом та освітленням.
10. Створювати `selected/`, `multiple_faces_review/`, `report.csv`, `summary.json` і `contact_sheet.jpg`.
11. Ніколи не змінювати оригінальні фотографії.

Не входило у перший MVP:

- GUI;
- тренування LoRA;
- редагування або кадрування оригіналів (пізніше додано окремі похідні кропи без зміни джерел);
- CUDA та інші GPU-бекенди;
- автоматичне видалення файлів;
- підтримка відео.

## 3. Запропонований стек

- Python 3.11 або 3.12;
- `opencv-python-headless`;
- `numpy`;
- `Pillow`;
- `pytest` для тестів;
- YuNet для детекції облич;
- SFace/MobileFaceNet для embeddings.

Спочатку використовувати FP32-моделі. INT8 варіанти перевіряти лише після отримання базових метрик: на старому x86 CPU квантизація не гарантує прискорення, а точність важливіша за кілька мегабайт.

## 4. Архітектура

```text
lora_face_select_lite/
  PLAN.md
  README.md                 # після старту реалізації
  pyproject.toml
  models/                   # моделі або інструкція їх завантаження
  lora_face_select_lite/
    cli.py
    backend.py              # YuNet + SFace, без бізнес-логіки
    analysis.py             # аналіз референсів і кандидатів
    quality.py              # різкість, експозиція, розмір, освітлення
    pose.py                 # груба оцінка ракурсу з landmarks
    selection.py            # score, diversity, duplicate rejection
    reports.py              # CSV, JSON, contact sheet, копіювання
    models.py               # dataclass-и результатів
  tests/
    unit/
    integration/
```

Потік обробки одного фото:

```text
read original
  -> resize for analysis (long side <= configurable limit)
  -> YuNet detect
  -> scale bbox/landmarks consistently
  -> align target faces
  -> SFace embeddings
  -> identity + quality + pose + duplicate metrics
  -> CandidateRecord
```

Після MVP додано окремий етап підготовки: BiSeNet ResNet18 сегментує обличчя й волосся у локальному ROI; MediaPipe PersonDet зіставляє target face з тілом; MediaPipe Pose повертає 33 landmarks і маску людини; body-aware cropper перевіряє перетин рук/ніг, запас біля суглобів і створює похідні `prepared/`. Дальні та сумнівні кадри не перетворюються примусово на портрети. Вихід завжди зберігає незмінені `selected/` для аудиту та відновлення.

Зображення потрібно читати способом, який підтримує Unicode-шляхи на Windows. EXIF orientation слід нормалізувати до детекції, інакше фото з телефона можуть аналізуватися боком.

## 5. Важливі технічні рішення

### Identity score

- Кожен референс повинен містити рівно одне обличчя.
- Embeddings референсів L2-нормалізуються, усереднюються і нормалізуються повторно.
- На фото з кількома обличчями обчислюється схожість кожного; target — максимум.
- Поріг InsightFace `0.35` не переноситься. Для SFace він визначається окремим калібруванням.
- У звіті зберігаються similarity, detection confidence, face count і причина рішення.

### Швидкодія

- Детектор працює на копії з довгою стороною орієнтовно 960 px; значення робиться параметром.
- Оригінал не тримається в пам'яті довше, ніж потрібно для метрик і копіювання.
- Обробка послідовна у MVP: паралельний запуск DNN може збільшити RAM і конкуренцію потоків OpenCV.
- Кількість потоків OpenCV задається явно і перевіряється benchmark-ом на 1, 2 та 4 потоках.
- Повторний запуск у наступній версії може використовувати cache за шляхом, розміром і `mtime`.

### Ракурс

YuNet дає лише 5 landmarks, тому pose bins будуть приблизними. Для MVP достатньо стабільно відрізняти:

- frontal;
- left/right three-quarter;
- left/right profile;
- unknown.

Категорії `up/down` не слід обіцяти, доки вони не пройдуть перевірку на реальних фото.

### Кілька облич

Фото з кількома обличчями можна включати у strong candidates, якщо потрібну людину знайдено за similarity і геометричний crop лишає всі інші detected face bbox за межами `prepared/`. Кадри з bbox, що перекривають target face, копіювати у `multiple_faces_review/`.

## 6. Етапи реалізації

### Етап 0 — контрольний набір і критерії

- Зібрати локальний приватний набір приблизно зі 100–300 фото: потрібна людина, інші люди, групові кадри, профілі, погане світло, розмиття.
- Розмітити мінімум: target present, usable for LoRA, multiple faces.
- Зафіксувати час поточного застосунку, якщо його можливо запустити на іншому ПК, та результат ручного відбору.

Результат: тестовий набір, який не потрапляє у git, і таблиця очікуваних рішень.

### Етап 1 — технічний spike

- Завантаження YuNet і SFace.
- Детекція, align/crop, embedding, cosine similarity.
- Прогін 20–30 характерних фото.
- Перевірка FP32 та, опційно, INT8.
- Замір часу й пікової RAM на цьому ThinkPad.

Умова переходу: моделі стабільно запускаються без GPU, правильна людина зазвичай має кращий score, ніж сторонні люди.

### Етап 2 — MVP CLI

- Команди `doctor` і `select`.
- Валідація input/output.
- Reference centroid, аналіз кандидатів, quality metrics.
- Відбір, дедуплікація, shortfall policy.
- Копіювання результатів та звіти.
- Прогрес `current/total`, бо CPU-аналіз може бути тривалим.

### Етап 3 — калібрування

- Побудувати розподіли score для same-person та different-person.
- Обрати safe default threshold з пріоритетом низьких false positives.
- Перевірити окремо профілі, окуляри, сильний макіяж, різний вік і погане світло.
- Винести threshold у CLI та записувати його у `summary.json`.

### Етап 4 — приймальне порівняння

- Порівняти Lite, поточний застосунок і ручну розмітку.
- Перевірити не лише identity accuracy, а й якість фінальних top-N наборів.
- Переглянути contact sheets без знання того, який застосунок їх створив.
- Зафіксувати швидкість, RAM, розмір моделей і помилки.

### Етап 5 — оптимізація після коректності

- Підібрати analysis resolution і кількість потоків.
- Додати cache.
- Лише тоді вирішити, чи виправдані INT8-моделі або нативна збірка.

## 7. Критерії готовності

Мінімально прийнятний результат на контрольному наборі:

- не менше 95% target-фото правильно проходять identity filter серед придатних кадрів;
- false positive для іншої людини — не більше 1%;
- жоден оригінальний файл не змінено;
- повторний запуск з тими ж параметрами дає той самий порядок;
- 100 типових фото обробляються на цьому ноутбуці не довше 5 хвилин;
- пікова RAM нижча за 1 ГБ;
- результати містять усі звіти та достатнє пояснення кожної відмови;
- ручний перегляд top-20 не виявляє сторонніх людей.

Числа 95%/1% є початковими product criteria, а не заявленою точністю моделей. Якщо контрольний набір покаже інший компроміс, критерії переглядаються до релізу, а не приховуються зміною порога.

## 8. Основні ризики

| Ризик | Вплив | Що робити |
|---|---|---|
| SFace гірше розрізняє складні фото | неправильна людина або пропуски | safe threshold, кілька референсів, review-зона |
| Поріг узято з InsightFace | некоректна класифікація | окреме калібрування SFace |
| 5 landmarks недостатньо для точного pose | слабший баланс ракурсів | грубі bins, `unknown`, ручний contact sheet |
| Зменшення фото приховує малі обличчя | false negative | configurable resolution, тест far shots |
| EXIF orientation не враховано | detector не бачить обличчя | нормалізація orientation перед OpenCV |
| Групове фото проходить автоматично | поганий LoRA-датасет | завжди відкладати multi-face у review |
| INT8 не швидший на Haswell | складність без користі | benchmark до увімкнення |
| Ліцензії моделей не перевірено для способу поширення | блокування релізу | зафіксувати джерело, версію, checksum і license |

## 9. Перше практичне завдання

Створити spike, який нічого не відбирає і не копіює, а лише друкує для кожного тестового фото:

```text
path | face_count | best_similarity | detection_score | elapsed_ms
```

Саме цей маленький spike відповість на два головні питання: чи достатньо SFace для конкретної людини та скільки реально займає обробка на цьому ноутбуці. Після нього можна коректно оцінити весь MVP.
